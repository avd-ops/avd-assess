# Intune and host management method

How to judge the way an estate manages its session hosts and the client devices that reach them: Intune for hosts and devices, against Group Policy where an estate keeps it. It is the [assessment](assessment.md) method applied to the Intune and host management pillar (`intune` in `dimensions.yaml`). Microsoft documents what Intune supports on AVD hosts, so the method links out to those pages and adds only the scope page (`gap:intune-scope`): which state to read, how devices map to pools, and which limits make a setting not applicable rather than missing.

## Method

1. **Ask how hosts are managed** before reading anything: Intune, Group Policy, both, or co-management; how hosts get Windows updates; and what client devices must prove to connect (`gap:intake`, `ref:review-checklists-avd#E01.03`).
2. **Check enrollment against the prerequisites:** a host pool deployed through Azure Resource Manager in Intune's tenant, agent 1.0.2944.1400 or later, one MDM provider, Entra join with enrollment or hybrid join with device credentials, no Entra Domain Services join, and an image captured before enrollment. Reader sees the enrollment request; whether hosts are managed needs an Intune read, and an enrolled host isn't yet a managed one (`ref:intune-avd-multisession#enrollment-prerequisites`, `ref:intune-avd-multisession#device-credentials`, `ref:intune-avd-multisession#one-mdm-provider`, `ref:intune-avd-multisession#no-entra-ds`, `ref:intune-avd-multisession#no-cloned-enrolled-image`, `obs:intune-enrolled-policies-left-to-owner`).
3. **Check configuration delivery:** settings catalog policies filtered to the multi-session edition, device settings to device groups and user settings to user groups, administrative templates through the catalog (`ref:intune-avd-multisession#settings-catalog-only`, `ref:intune-avd-multisession#device-and-user-scope`, `ref:intune-avd-multisession#admx-supported`).
4. **Where Group Policy stays, check for one owner per setting:** the GPOs on the hosts' OU reviewed, and no setting through both channels unless MDMWinsOverGP covers it. Group Policy wins by default (`ref:review-checklists-avd#D01.03`, `ref:mdm-wins-over-gp#default-gp-wins`, `ref:mdm-wins-over-gp#policy-csp-only`, `ref:intune-group-policy-analytics#mdm-support-percentage`).
5. **Check the security baseline delivered** against the host baseline profile: the version for the hosts' Windows release, never a preview, with recorded departures (`ref:intune-avd-multisession#baselines-available`, `ref:intune-security-baselines#versioned-per-release`, `ref:intune-security-baselines#no-preview-in-production`, `gap:host-baseline-profile`).
6. **Check host compliance:** a device-targeted policy using the settings multi-session supports, and the tenant set so a device with no policy is noncompliant, because the default counts it compliant (`ref:intune-avd-multisession#compliance-settings-supported`, `ref:intune-avd-multisession#compliance-device-targeted`, `ref:intune-compliance#no-policy-default-compliant`, `ref:graph-device-management-settings#secure-by-default`).
7. **Check what client devices must prove:** Intune compliance for managed devices and app protection for unmanaged phones, tablets and the browser, both through Conditional Access, which the identity pillar judges (`ref:ca-require-compliant-device#compliance-signal`, `ref:windows-app-device-compliance#app-protection-for-clients`, `ref:review-checklists-avd#G04.01`).
8. **Check apps and updates against what multi-session supports:** apps in system context, targeted to devices, Required; no update rings or Autopatch on multi-session, where the image carries updates and Intune only sets quality update behavior; Autopatch on personal single-session hosts only (`ref:intune-avd-multisession#apps-system-required`, `ref:intune-avd-multisession#quality-updates-catalog-only`, `ref:autopatch-avd#personal-only`, `ref:avd-update-methods#multisession-image-based`, `ref:review-checklists-avd#E01.09`).
9. **Check the device lifecycle:** no wipe, retire or lock on multi-session hosts, and the step that removes a host removes its Entra ID and Intune records (`ref:intune-avd-multisession#remote-actions-unsupported`, `ref:intune-avd-multisession#orphaned-records`, `obs:device-records-outlive-hosts`).
10. **Check the one profile setting Intune depends on:** identity tokens don't roam (`ref:intune-avd-multisession#no-token-roaming`, `ref:fslogix-settings#roamidentity-off`).
11. **Score what multi-session can't receive as not applicable,** never as a gap, and record what stays `unknown` and why: no Intune read, no host read, or no operator answer (`gap:intune-scope`).

## Not yet known

- No check runs yet. The facts are `specified` in the fact register, and avd-current-state has no Intune read; the draft checks are in `gap:intune-scope`.
- Whether matching Intune devices to host pools by name holds on a real estate, including hosts renamed or rebuilt under the same name. A sandbox run with enrolled hosts settles it; it waits on a cost estimate and the owner's go.
- How long Intune's own cleanup takes to remove records of deleted multi-session hosts; Microsoft gives no guarantee (`ref:intune-avd-multisession#orphaned-records`).
