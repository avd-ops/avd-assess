# Reliability method

How to judge whether an estate stays available through a host or zone failure and comes back after a region loss, a deletion or a bad change, against what Microsoft publishes for AVD. It is the [assessment](assessment.md) method applied to reliability, availability zones, backup, business continuity and disaster recovery, and it is a map: each step points at the pinned source, the fact that measures it and the check that judges it, and says so where none exists. Nothing here restates Microsoft's guides; read them at the pin. The rows are `reliability.*`, `profile.backup-copy` and `profile.cross-region` in [dimensions.yaml](../dimensions.yaml); the review checklist's A01 to A03 items are all on a row.

AVD has no disaster recovery of its own (`ref:avd-bcdr-concepts#no-native-dr`). Microsoft runs and fails over the control plane (`ref:avd-service-resilience#control-plane-microsoft`); the hosts, profiles, apps, user data and identities are the customer's (`ref:avd-bcdr-concepts#customer-managed-components`). The method judges only the customer's part.

## Method

1. **Targets first.** Each workload's RTO, RPO and expected availability come from the business, not from the platform: the AVD service has no financially backed SLA (`ref:review-checklists-avd#A01.01`, `ref:waf-reliability-checklist#RE:04`, `ref:caf-avd-bcdr#no-financial-sla`). Intake `intake.recoveryTime` and `intake.recoveryPoint`, for the strictest workload while intake is per estate; without them every later step can only describe, not judge. Row `reliability.targets`.
2. **Critical workloads in their own pools**, so each pool can take the recovery model its targets need (`ref:review-checklists-avd#A01.03`, `ref:caf-avd-bcdr#separate-critical-apps`). The use case record names them ([use cases](use-cases.md)). Row `reliability.critical-pools`.
3. **Zones for availability**, with hosts to spare for a lost zone, fixed when the VMs are created (`ref:review-checklists-avd#A01.04`, `ref:avd-multiregion-bcdr#spread-and-overprovision`, `ref:caf-avd-bcdr#availability-option-at-create`). Zones are not disaster recovery (`ref:avd-multiregion-bcdr#zones-not-dr`). Row `reliability.zones`.
4. **A recovery model per pool** for a region loss: rebuild, restore, warm standby (active-passive) or active-active, chosen from the targets and `intake.regionRecovery` (`ref:review-checklists-avd#A01.02`, `ref:avd-multiregion-bcdr#active-active-vs-passive`). Microsoft's RTO and RPO per model are estimates (`ref:avd-multiregion-bcdr#rto-rpo-by-model`, `ref:avd-multiregion-bcdr#estimates-to-test`); recovery-region capacity is guaranteed only for running VMs or a reservation (`ref:avd-multiregion-bcdr#capacity-not-guaranteed`, `ref:capacity-reservation#reserves-capacity`); standby hosts start every 90 days (`ref:avd-multiregion-bcdr#token-refresh-90-days`). Row `reliability.dr-model`.
5. **Personal pools** hold state: Site Recovery per VM, to another zone or region, never its test failover on session hosts (`ref:review-checklists-avd#A01.06`, `ref:avd-multiregion-bcdr#personal-site-recovery`, `ref:avd-multiregion-bcdr#no-asr-test-failover`, `ref:asr-zone-to-zone#may-fall-short-region-wide`). Row `reliability.personal-hosts`.
6. **No VM backup for pooled hosts**; they are rebuilt from the image (`ref:review-checklists-avd#A01.05`, `ref:caf-avd-bcdr#hosts-stateless-no-vm-backup`). Row `reliability.host-backup`.
7. **The image is where the pool will be rebuilt**: each version replicated to both regions on zone-redundant storage, and a gallery in each region (`ref:review-checklists-avd#A02.01`, `ref:compute-gallery#two-galleries-for-dr`, `ref:compute-gallery#zrs-replicas`). Row `reliability.image-regions`.
8. **Dependencies come too**: domain controllers with DNS, sync staging, hub and hybrid links, line-of-business apps, app packages per region and a log workspace that survives; the directory's configuration exported as a known-good state (`ref:review-checklists-avd#A02.02`, `ref:caf-avd-bcdr#dependencies-in-recovery-region`, `ref:avd-multiregion-bcdr#identity-in-recovery-region`, `ref:avd-multiregion-bcdr#msix-account-per-region`, `ref:avd-multiregion-bcdr#log-workspace-per-region`, `ref:entra-recoverability#document-known-good`). Intake `intake.recoveryDependencies`; most of it is outside what a Reader can see. Row `reliability.dependencies`.
9. **Decide what profile data matters** before protecting it (`ref:review-checklists-avd#A03.01`, `ref:caf-avd-bcdr#assess-what-to-protect`, `ref:avd-multiregion-bcdr#office-container-no-backup`). Intake `intake.profileData`. Row `reliability.profile-data`.
10. **Profile copies that survive the account** (`ref:review-checklists-avd#A03.02`): zone-redundant storage for availability (`profile.resilience`), a vaulted backup for an offsite copy (`ref:review-checklists-avd#A03.04`, `ref:files-backup#vaulted-survives-source-loss`), and a backup whose last job succeeded, since Microsoft's pages differ on the key access it needs (`ref:files-backup-support#key-access-needed`, `ref:files-backup-portal#keys-or-private`, `obs:files-backup-key-access-off`). Row `profile.backup-copy`.
11. **Profiles across regions**: Cloud Cache rather than storage replication; one pool per user at a time; Azure NetApp Files by its own replication (`ref:review-checklists-avd#A03.03`, `ref:review-checklists-avd#A03.06`, `ref:avd-multiregion-bcdr#cloud-cache-over-storage-replication`, `ref:files-redundancy#geo-only-hdd`, `ref:anf-replication#zone-and-region-together`). Row `profile.cross-region`.
12. **Proven by a test**: a restore and a failover with a test group, timed against the targets, then a full failover and failback, kept where it survives the outage (`ref:waf-disaster-recovery#RE:09`, `ref:waf-disaster-recovery#drills-prove-targets`, `ref:avd-multiregion-bcdr#selective-failover-test`, `ref:avd-multiregion-bcdr#automate-and-align`). The evidence is a run record, not a setting. Row `reliability.recovery-test`.

## Where reliability lives in the family

avd-assess holds this map and method. avd-current-state collects the facts and runs the checks from a pinned copy. avd-landing-zone builds same-tenant recovery: a recovery region, a status check, a configuration snapshot and recovery tests in tiers from rebuild to warm standby, each recovery action a run record ([recovery spec](https://github.com/avd-ops/avd-landing-zone/blob/91c7acf2924ccf3cf82458b3969c0f3fbb9db2bc/build/specs/recovery-spec.md)); active-active is outside it, and the method still maps it because Microsoft documents it. The evidence each step needs, the draft checks and the facts they wait for are in `gap:reliability-scope`.

## Not yet known

- The draft checks in `gap:reliability-scope` cite facts the register lists as `specified`; each enters method.json with its facts.
- Whether the landing zone's default profile backup runs with key access off (`obs:files-backup-key-access-off`), and whether any tier meets its targets (`obs:recovery-tiers-not-yet-tested`).
- Two Microsoft pages disagree on Azure NetApp Files zone and region replication on one volume (`ref:avd-multiregion-bcdr#anf-zone-or-region`, `ref:anf-replication#zone-and-region-together`); the product's own page is read as current.
