# Desktop DevOps method

How to apply DevOps -- versioned infrastructure and policy-as-code, offline read-only sensing, deterministic standards checks, and gate-checked remediation -- across Azure Virtual Desktop (`avd`), Windows 365 Cloud PCs (`win365`) and Microsoft Intune (`intune`). The full architectural writeup and traceability matrix are in [docs/desktop-devops.md](../docs/desktop-devops.md).

## Method

1. **Scope the desktop platforms in intake before evaluating checks:** record `intake.avdScope` (`pooled`, `personal`, `both`, `not-used`) and `intake.win365Scope` (`not-used`, `enterprise`, `frontline`, `both`) alongside the user personas (`use-cases.yaml`) so checks for unused platforms evaluate to `not-applicable` rather than false gaps (`gap:intake`, `gap:desktop-devops-scope`, `gap:scoring`).
2. **Version all five control planes as code in Git:** define AVD compute, storage and networking in Bicep (`avd-azure`), Entra groups and Conditional Access covering both AVD and Windows 365 application IDs (`avd-entra`), Intune Settings Catalog profiles, compliance policies, platform assignment filters and Windows 365 provisioning policies and user settings as Graph JSON (`avd-intune`), Microsoft 365 shared activation and OneDrive/Teams VDI policies (`avd-m365`), and Power Platform DLP boundaries (`avd-power-platform`) (`gap:deployment-dimensions`, `gap:desktop-devops-scope`).
3. **Isolate desktop platforms with Intune assignment filters:** deploy explicit assignment filters for multi-session AVD hosts (`device.osSku -eq "ServerRdsh"`), personal AVD hosts, Windows 365 Cloud PCs (`device.model -startsWith "Cloud PC"`) and physical workstations, and verify that no workstation-only policy targets All Devices without a filter (`ref:windows-365-intune#assignment-filters-separate-platforms`, `ref:intune-avd-multisession#settings-catalog-only`, `gap:intune-scope`).
4. **Collect live state read-only and redact offline into contract C11:** read Azure Resource Graph, Entra ID, Intune and Windows 365 (`deviceManagement/virtualEndpoint`) without write permissions, and emit a zero-PII `avd-current-state-facts/v1` snapshot whose fields map to registered `C15` fact IDs (`gap:collection-map`, `gap:intune-scope`, `gap:desktop-devops-scope`).
5. **Evaluate multi-session AVD and Windows 365 Cloud PC baselines deterministically:** run `method.json` against the `C11` snapshot and `C19` intake to check Intune secure-by-default compliance (`asm-intune-no-policy-noncompliant`), FSLogix, RDP Shortpath and session limits (`asm-intune-fslogix-configured`, `asm-intune-shortpath-configured`, `asm-intune-session-limits-configured`), absence of update rings on multi-session pools (`asm-intune-no-multisession-update-ring`), and -- when Windows 365 is in scope -- provisioning policy SSO (`asm-win365-sso-enabled`), no persistent local administrator (`asm-win365-no-local-admin`), restore-point frequency within 24 hours (`asm-win365-restore-points-24h`), Azure Network Connection health (`asm-win365-anc-healthy`) and Cloud PC device compliance (`asm-win365-cloudpcs-compliant`) (`ref:windows-365-intune#provisioning-policy-sso`, `ref:windows-365-intune#user-settings-least-privilege`, `ref:windows-365-intune#restore-point-cadence`, `ref:windows-365-intune#anc-health-checks`, `ref:windows-365-intune#cloudpc-intune-compliance`).
6. **Evaluate consumption and license FinOps side by side:** check AVD hourly compute and storage utilization (autoscale, Start VM on Connect, right-sizing against `C12` concurrency) alongside Windows 365 step-function license utilization (`c11.entra.skuWin365Available` and provisioned Cloud PCs with zero connections) (`ref:waf-cost-optimization-checklist#CO:05`, `ref:review-checklists-avd#E01.05`, `gap:finops-scope`, `gap:desktop-devops-scope`).
7. **Route fleet policy drift to GitOps pull requests and tactical host or Cloud PC actions to gate-checked plans:** propose Intune Settings Catalog, compliance and assignment filter fixes as policy-as-code pull requests (`desktopDevOpsAction: policy-pr` against `avd-intune`), and require every destructive runtime action (`reprovision`, `deprovision`, `replace-session-host`) to pass the governance gate's session-drain preconditions and `D1` data-loss guard (`restorePointVerified: true` with `restorePointAgeHours <= 24`, or `discardLastCopyApproved: true`) before a human approves in the GitHub Environment (`ref:intune-avd-multisession#remote-actions-unsupported`, `ref:windows-365-intune#restore-point-cadence`, `gap:remediation-plan`, `gap:desktop-devops-scope`).

## Not yet known

- Whether Microsoft Graph's `deviceManagement/virtualEndpoint/cloudPCs` connection-quality and last-sign-in reports expose sufficient granularity across both Enterprise and Frontline Cloud PCs without requiring Log Analytics or an endpoint agent (`gap:desktop-devops-scope`, `gap:intune-scope`).
- How quickly Intune assignment filter evaluation converges when a session host or Cloud PC is reprovisioned under an existing device name (`obs:device-records-outlive-hosts`, `gap:intune-scope`).
