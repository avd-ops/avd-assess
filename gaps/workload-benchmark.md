# Gap: a workload benchmark before sizing

**Searched (2026-10-21):** the AVD review checklist (`ref:review-checklists-avd#C01.10`), the session host sizing guide (`ref:session-host-sizing#capacity-approaches`, `ref:session-host-sizing#estimates-only`), the Well-Architected performance testing guidance (`ref:waf-performance-testing#hypothesis-baseline-variant`, `ref:waf-performance-testing#record-baselines`), the AVD load balancing page (`ref:avd-load-balancing#set-limit-from-insights`), Microsoft Learn and the web. **Not found:** an open, published workload definition for AVD hosts, or a pass threshold for one. The checklist says to run a workload test before choosing a size; the sizing guide names two ways (a pilot, or simulation tools that ramp scripted users) and says its own numbers are estimates; neither says what the test runs, how long, or what counts as a pass. Simulation products exist as a category, each with its own workload and score; none is open or comparable across them.

**What we write.** How a benchmark is run so its result can stand in for the sizing guide's estimates, and where its result goes. The pass criteria are the baseline profile's, not new ones.

1. **The workload is the persona's, not a product's.** Each test names the workload class from the persona record (`gap:use-cases`) or the sizing guide's examples (`ref:session-host-sizing#workload-types`), and the apps it opens come from the persona's app list. A test that can't say which persona it stands for doesn't size anything.
2. **Pilot first, simulation where there are no users yet.** A pilot with real users on one host is the stronger evidence (`ref:session-host-sizing#capacity-approaches`); a scripted ramp is accepted where no pilot is possible, and its record says so. Any load generator may be used (an open-source one, or a third-party simulation product, as a category); the record names the category and the script's version, never a score from a closed product as the result.
3. **Ramp one host to the gate.** Add sessions in steps on one host of the candidate size until a target in the baseline profile fails (`gap:baseline-profile`); the step before the failure is the measured density. Include a sign-in storm at the start, because concurrent sign-ins are the costliest minutes (`ref:session-host-sizing#logon-storm-headroom`).
4. **Measure the same facts a live estate gives.** CPU per user, memory per user, disk IOPS, logon time and round trip as the C12 facts the baseline profile reads (`c12.group.perUser.*`, `c12.group.logonSeconds.p95`, `c12.group.rttMsP95`), so a benchmark and a later sample check (`gap:sample-check`) compare like for like.
5. **One change per run.** Size, family, density or image change one at a time, with the run before as the baseline (`ref:waf-performance-testing#hypothesis-baseline-variant`), as the tuning loop does (`gap:tune-loop`).
6. **The result is evidence, not a verdict on the size.** It goes in through the evidence intake (`gap:evidence-intake`) with the size, image version and persona, and a person decides whether it replaces the estimate for that class. Headroom on top of the measured density is the operator's choice; no source sets a number (`ref:session-host-sizing#logon-storm-headroom`).

Retire this page when Microsoft or a standards body publishes an open AVD workload and pass threshold; the steps then cite it.
