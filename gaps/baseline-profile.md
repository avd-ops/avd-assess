# Gap: a baseline profile of what good looks like

**Searched (2026-10-20):** Microsoft Learn (the session host sizing guide `ref:session-host-sizing`, AVD Insights and its glossary, connection quality, prerequisites, autoscale, Advisor's right-size criteria `ref:advisor-vm-rightsize`, Windows performance troubleshooting), the Well-Architected performance pillar (`ref:waf-performance-checklist`, `ref:waf-performance-targets`, `ref:waf-performance-testing`, `ref:waf-continuous-performance`), the FinOps workload optimization capability (`ref:finops-workload-optimization`), the AVD review checklist, WDOT, GitHub and the web. **Not found:** one published profile that puts, for an AVD host pool of a given workload, the experience targets, the utilization a host should run at, and the density range side by side, with the window and statistic to measure them. The sources each hold a piece: the sizing guide has density and minimum sizes per workload, Insights has experience bands, Windows guidance has CPU bands, Advisor has the utilization a smaller size must stay under, and the Well-Architected pillar says to set targets as percentiles and keep baselines. Also not found: memory per user, a memory ceiling for a session host, disk latency for a session host, and the share of a host's hours that may sit over a band. Commercial experience scores exist, but they tune their thresholds per customer and aren't open, so we cite none.

**What we write.** [baselines.yaml](../baselines.yaml) assembles the pieces into one profile per workload class, and the [baseline profile method](../methods/baseline-profile.md) says how an estate gets its own.

1. **One window for everything.** At least the seven days Advisor reads by default (`ref:advisor-vm-rightsize#lookback`), covering the busiest days, in percentiles (`ref:waf-performance-targets#percentiles`).
2. **Judge utilization in working hours only.** A pooled host that a scaling plan keeps nearly idle overnight isn't waste; Advisor itself says low use can be by design (`ref:advisor-vm-rightsize#not-always-applicable`). Ramp-up and peak hours come from intake (`gap:intake`).
3. **Experience is a gate, utilization is a band.** A host that fails an experience target is a finding whatever its CPU; a host in the `under` band is a rightsizing candidate only while every experience target holds. Overperformance and underperformance are both findings (`ref:waf-continuous-performance#over-and-under`).
4. **Bands from two published sources.** The `under` band is Advisor's resize rule (`ref:advisor-vm-rightsize#user-facing-targets`): if the next size down would still sit at P95 CPU of 40% or less and P99 memory of 60% or less, the host is bigger than it needs to be. The `good`, `watch` and `over` bands are the Windows CPU bands (`ref:perfmon-troubleshooting#cpu-bands`). We put the two together; neither source does.
5. **Density is a range with a measured top.** It starts at or under the sizing guide's users per vCPU for the class (`ref:session-host-sizing#multisession-users-per-vcpu`), which the guide calls an estimate (`ref:session-host-sizing#estimates-only`). The measured density, defined in [baselines.yaml](../baselines.yaml), replaces it: the most sessions per host at which every experience target holds at peak and CPU stays out of the `over` band.
6. **No number where none is published.** Memory above 60%, disk latency, logon time and app load time start as the estate's own first P50 and P95 (`gap:sample-check`, `gap:logon-target`), and later runs judge change against that.
7. **Classes, not people.** A host pool's class comes from its persona record in the use case method, or from the sizing guide's examples when there is no record. A persona may tighten a target, never loosen it without a recorded reason.

**How it changes.** A value moves to `published` the day a source states it. A value that measured runs keep contradicting gets a `disagrees` observation and the gold-standard registry demotes it (`gap:gold-standards`).

**Not yet known.** No profile value has been checked against users we measured (`obs:users-per-vcpu-adopted`). The 40% and 60% headroom figures come from a cost tool for all user-facing VMs, not from AVD testing. The two-tier benchmark profiles in [benchmarks/profiles.yaml](../benchmarks/profiles.yaml) (`gap:workload-benchmark`) and Contract C25 (`avd-benchmark-result/v1`) define how each prior and `not-yet-tested` observation is measured and submitted.
