# Gap: Desktop DevOps across Azure Virtual Desktop, Windows 365 and Microsoft Intune

**Searched (2026-11-02):** Microsoft Learn documentation for Azure Virtual Desktop (`ref:avd-management`, `ref:review-checklists-avd`), Windows 365 Enterprise and Frontline provisioning, user settings, restore points and Azure Network Connections (`ref:windows-365-intune`), Intune multi-session and personal desktop management (`ref:intune-avd-multisession`, `ref:intune-avd-personal`, `ref:intune-settings-catalog`, `ref:intune-compliance`, `ref:autopatch-avd`), the Well-Architected Framework checklists (`ref:waf-reliability-checklist`, `ref:waf-cost-optimization-checklist`), the FinOps Framework, and open-source Intune and AVD repositories on GitHub. **Not found:** an open, vendor-neutral methodology that joins Azure Virtual Desktop (`avd`), Windows 365 Cloud PCs (`win365`) and Microsoft Intune policy-as-code (`intune`) into a single continuous DevOps loop covering platform assignment filter isolation, dual-surface FinOps (hourly consumption vs. step-function seat licensing), restore-point data-loss guards before reprovisioning, and separated write paths for fleet policy-as-code pull requests versus tactical host and Cloud PC actions.

## Why a unified Desktop DevOps method is needed

Microsoft documents AVD in Azure docs, Windows 365 under `deviceManagement/virtualEndpoint` in Graph and Intune docs, and Settings Catalog and compliance in Intune docs. In a real estate, all three share:

1. **One identity and Conditional Access plane (`entra`):** Users sign in through the same `Windows App` client to both AVD session hosts and Windows 365 Cloud PCs, governed by Conditional Access policies that must include both application IDs (`ref:ca-require-compliant-device#compliance-signal`, `ref:windows-365-intune#provisioning-policy-sso`).
2. **One Intune policy and compliance plane (`intune`):** Settings Catalog profiles, security baselines, update rings and compliance policies evaluate across AVD multi-session hosts, AVD personal hosts, Windows 365 Cloud PCs and physical desktops in the same tenant (`ref:intune-avd-multisession#settings-catalog-only`, `ref:windows-365-intune#assignment-filters-separate-platforms`).
3. **One stateful user-data constraint:** Destructive lifecycle actions (reprovisioning a Cloud PC or replacing a session host) risk losing local state or interrupting active sessions unless guarded by deterministic session and restore-point checks (`ref:windows-365-intune#restore-point-cadence`, `ref:intune-avd-multisession#remote-actions-unsupported`).

## What this gap specifies

The full architecture and stage-by-stage design are in [docs/desktop-devops.md](../docs/desktop-devops.md), and the step-by-step assessment and operating procedure is in [methods/desktop-devops.md](../methods/desktop-devops.md):

| Area | Rule in this methodology | Where it is implemented |
|---|---|---|
| **Intake-gated platform scope** | `intake.avdScope` and `intake.win365Scope` (`C19`) scope which desktop platforms the estate runs; checks for unused platforms evaluate to `not-applicable`, never `gap` (`gap:scoring`) | `contracts/schemas/intake.schema.json`, `method.json` (`when` clauses) |
| **Mandatory platform assignment filters** | Every tenant managing more than one Windows platform defines explicit Intune assignment filters (`avd-multisession`, `avd-personal`, `win365-cloudpc`, `physical-desktop`) and avoids unfiltered All-Devices configuration assignments (`ref:windows-365-intune#assignment-filters-separate-platforms`) | `avd-intune` (`profiles/filters/*.json`), `method.json` (`asm-intune-assignment-filters-separate-platforms`) |
| **Cloud PC baseline and resilience posture** | When Windows 365 is in scope, provisioning policies enable single sign-on, user settings disable persistent local administrator and set restore points at 4 to 24 hours, Azure Network Connections pass health checks, and Cloud PCs evaluate as compliant (`ref:windows-365-intune#provisioning-policy-sso`, `ref:windows-365-intune#user-settings-least-privilege`, `ref:windows-365-intune#restore-point-cadence`, `ref:windows-365-intune#anc-health-checks`, `ref:windows-365-intune#cloudpc-intune-compliance`) | `avd-intune` (`profiles/win365/*.json`), `avd-current-state` (`Get-AvdStateIntune`), `method.json` (`asm-win365-*`) |
| **Data-loss guard on destructive actions (`D1`)** | Reprovisioning or deprovisioning a Cloud PC or replacing a session host requires a verified restore point within 24 hours (`restorePointVerified: true`, `restorePointAgeHours <= 24`) or explicit owner approval (`discardLastCopyApproved: true`) | `avd-second-brain` (`C9`), `avd-swarm` (`gate/avd_gate/evidence.py`) |
| **Separated write paths** | Fleet-wide Intune Settings Catalog, compliance and assignment filter changes are proposed as policy-as-code pull requests (`desktopDevOpsAction: policy-pr` to `avd-intune`); single-host or single-Cloud-PC operational actions go through `avd-swarm`'s human-approved `approve` environment | `avd-intune`, `avd-swarm` (`governance/allowlists/intune.yml`, `runbooks/intune/policy-drift.md`) |
| **Dual-surface FinOps** | AVD is judged on hourly compute/storage consumption and autoscale (`methods/finops.md`), while Windows 365 is judged on unassigned license seats (`c11.entra.skuWin365Available`) and inactive provisioned Cloud PCs | `avd-current-state` (`avd_current_state_facts.ps1`), `avd-swarm` (`governance/allowlists/cost.yml`) |
