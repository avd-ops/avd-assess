# Gap: what an identity assessment can see, and what it can't yet

**Searched (2026-10-21):** the AVD identity and authentication pages (`ref:avd-authentication`, `ref:avd-prerequisites#identity-scenarios`, `ref:avd-sso`, `ref:avd-mfa-conditional-access`, `ref:avd-entra-joined-hosts`), Azure Files and FSLogix identity pages (`ref:files-entra-kerberos`, `ref:fslogix-entra-profile`, `ref:files-ad-ds-password`), the review checklist's identity items (`ref:review-checklists-avd#D03.02`), the Cloud Adoption Framework's AVD identity page (`ref:caf-avd-identity`, deprecated), the security benchmark's AVD baseline (`ref:mcsb-avd-baseline#IM-7`), the Resource Graph table reference (`ref:resource-graph-tables`). **Not found:** a published way to assess an AVD estate's identity setup from data a tool can read: the sources say what to configure, but nothing lists which of it a control plane read sees, which needs a directory read, and which only the operator knows. No source gives a number for sign-in frequency, admin role counts or the share of users assigned directly.

**What we write.** The identity pillar's rows in [dimensions.yaml](../dimensions.yaml) (pillar `identity`) and three kinds of evidence for them.

| Evidence | What it sees | Rows | Facts |
|---|---|---|---|
| Control plane (Reader, Resource Graph and REST) | Join type per host (the VM's join extension), the host pool's single sign-on and redirection properties, the profile share's identity source, application group and subscription role assignments | `identity.scenario`, `identity.sso` (host pool half), `identity.sign-in-methods` (in-session half), `identity.files-auth`, `identity.app-group-assignment`, `identity.admin-access` | `c11.hostPool.sessionHosts.entraJoined`, `c11.hostPool.sessionHosts.domainJoined`, `c11.hostPool.entraSso`, `c11.hostPool.directUserAssignments`, `c11.subscription.privilegedAssignments` (all `specified`), `c11.storage.filesIdentity`, `c11.hostPool.redirection.webAuthn`, `c11.hostPool.redirection.smartCards` (built) |
| Directory read (Microsoft Graph, read-only) | Directory sync state, Conditional Access policies on the two AVD apps, per-user MFA, Security Defaults, sign-in frequency, the Windows Cloud Login service principal's Remote Desktop setting and trusted device groups, the storage app's MFA exclusion, LAPS | `identity.sso` (tenant half), `identity.mfa-conditional-access`, `identity.sign-in-frequency`, `identity.device-conditions`, `identity.directory-sync`, `identity.local-admin-password` | `proposed:c11.directory.*`; no collector reads the directory yet |
| Intake (the operator) | The planned join type and identity source, single sign-on choice, MFA scope, client devices, sign-in methods, external users | every row whose evidence is incomplete | `intake.identityConstraints`, `intake.avdMfa` (built); `intake.joinType`, `intake.userIdentitySource`, `intake.sso`, `intake.mfaScope`, `intake.clientDevices`, `intake.signInMethods`, `intake.externalUsers` (`specified`, `gap:intake`) |

Active Directory itself (domain controllers, OUs, GPOs, the join account) is outside every collector: `identity.domain-services` and `identity.domain-join-account` stay on intake or `none`, and `identity.ou-and-group-policy` is `host-side` (what a session host's applied policy shows).

**Rules for the method.**

1. **A directory fact never comes from a guess.** Until a read-only directory collector exists, its rows are `unknown` unless the operator answers the intake question; the intake answer is recorded as the operator's, not as a measurement. Whether avd-current-state gets an opt-in, read-only directory read is the owner's decision (the map plan's section 6), and every `directory` row in the pillar waits on it.
2. **One identity per user, one join type per pool.** A pool with both Entra joined and domain-joined hosts is a finding (`ref:avd-entra-joined-hosts#one-join-type-per-pool`), and a sign-in that uses a different Windows account than the Entra one is unsupported (`ref:avd-authentication#one-identity`). The control plane can't tell hybrid joined from AD-only hosts, so a mix of those two needs the directory read.
3. **Sources that disagree are recorded, not resolved by preference.** The prerequisites and Entra joined hosts pages still say FSLogix on Entra joined hosts needs hybrid users, while the Azure Files and FSLogix pages support cloud-only users; our own run agrees with the newer pages (`obs:fslogix-cloud-only-users-work`). The method follows the run and the newer pages, in the Azure public cloud only.
4. **Admin access and assignment are scored as trade-offs** (`warn`), because no source sets a count; the check, when one is written, reports the number and the scoped roles in use.
5. **Names never leave the estate.** Role assignment and policy facts are counts, enums or booleans; no user, group, policy or app name or ID goes into a fact (the register's privacy classes).
6. **The identity decision is intake-only today.** The register's `identity` decision is decidable from intake and forensic facts; when the join type and single sign-on facts are built, the decision should also list the azure tier, in the same pull request that marks them built.

**Overlaps.** Session limits and lock timing are `protocol.session-limits`; SMB channel and ticket encryption are `encryption.profile-transit`; Intune against Group Policy, and the compliance policies Conditional Access reads, are the intune pillar's; which client devices users bring is the endpoints pillar's; local administrator rights on hosts are the security posture pillar's (`ref:review-checklists-avd#G03.03`).
